# 0001. Зерно AppliedCharge — свёртка ingestion, коллекция внутри Budget

Дата: 2026-09-20
Статус: Принято

## Контекст

Инварианты 1–2 требуют помнить, какие биллинговые записи уже учтены
и какая сумма была в последний раз. Первая модель клала `AppliedCharge[]`
внутрь `Budget`.

CUR-подобный поток — это 10⁵–10⁷ строк на аккаунт в месяц, пачкой
за минуты. Вопрос: что ломается, если миллион id живёт в агрегате,
и куда этот журнал кладут в проде.

Ограничения: инварианты порогов, гистерезиса, закрытого лимита и валюты
остаются внутри `Budget`. Ожидаемая ошибка — `Result`. Между сервисами
нет общих таблиц.

## Рассмотренные варианты

### Вариант A. Все applied id внутри Budget

Каждый apply грузит и пишет весь набор записей периода.

Плюсы: инварианты 1–2 проверяются в одном объекте; тесты без БД;
один `SaveChanges`.

Минусы: загрузка 10⁶ сущностей — сотни МБ и мёртвый change tracker.
Любой apply поднимает версию агрегата: при пакетной доставке CUR
все линии одного бюджета сериализуются в одну строку (hotspot),
конфликты начинаются далеко до миллиона. Закрытый период с миллионом
детей нельзя дёшево поправить. Снапшот/replay неподъёмны.

### Вариант B. Сжать зерно на входе, коллекцию оставить в агрегате

Ingestion сворачивает CUR в ключ вроде (бюджет, usage date, сервис).
В периоде ~30–10³ элементов, A снова «влезает».

Плюсы: инварианты остаются в агрегате; write-hotspot падает
на число зёрен, не линий; так устроены AWS Budgets / Cost Explorer —
бюджет смотрит на агрегат, не на сырой CUR.

Минусы: «запись» из инварианта 2 — уже не линия провайдера.
Коррекция одной CUR-строки размазывается по rollup. Нельзя ответить
«какая линия толкнула 80%» из агрегата. Не спасает, если продукт
всё же обязан учитывать линии (детализация, explain).

### Вариант C. Журнал снаружи, в Budget — снимок

`Budget` хранит периоды, лимит, spent, защёлки порогов.
`AppliedCharge` — отдельная запись с уникальным ключом
`(BudgetId, BillingRecordId)` и последней суммой.

Применение в одной UoW: прочитать предыдущую сумму (или 0) →
дельта → `Budget.Apply(delta, currency, usageDate)` → upsert журнала.
Повтор с той же суммой — no-op журнала, агрегат не трогаем.
Конфликт уникального ключа = уже учтено.

Плюсы: загрузка Budget не растёт с CUR. Идемпотентность — точечный
lookup + уникальный индекс, как в ledger (баланс + проводки).
Инварианты 3–7 остаются в агрегате. Масштаб 10⁶ — это размер таблицы,
не размер агрегата.

Минусы: инварианты 1–2 больше не замкнуты в `Budget`; их держит
связка «уникальный ключ + last amount + один UoW». Забыли записать
журнал — следующий повтор допишет spent ещё раз. Handler координирует
два объекта; пороги нельзя утащить в handler. Штучный `Apply(delta)`
на каждую CUR-линию по-прежнему бьёт в одну строку Budget.

## Решение

Вариант B.

Ingestion сворачивает вход до зерна `(бюджет, дата потребления, сервис)`.
Коллекция `AppliedCharge` остаётся внутри `Budget`.

При таком зерне в периоде сотни записей, не миллион: месячный бюджет
с двумя десятками сервисов — это порядка 30 × 20 элементов. Загрузка,
change tracker и версия агрегата остаются в рабочей зоне. Проблема
масштаба из контекста не возникает, пока зерно держится.

Вариант A не выбран: сырой CUR в коллекцию класть нельзя, даже если
структура агрегата та же. Вариант C не выбран: он выносит инварианты 1
и 2 из агрегата в связку «уникальный индекс + handler». Они перестают
проверяться доменными тестами без БД — а это главная ценность модели.
Пороги и гистерезис тогда остаются в `Budget`, а «учтено ровно раз»
и «исправление = дельта» — нет.

Минусы B принимаем: коррекция одной CUR-строки видна только как смена
суммы зерна за день/сервис; line-level explain из агрегата не получить.

## Оценка масштаба

N — число `AppliedCharge` в одном агрегате за месячный период.
Загрузка EF Core — порядковая оценка: ~1.5 мкс на отслеживаемую
сущность (материализация + change tracker), не бенчмарк.

| Вариант | N на агрегат | Загрузка EF Core |
|---|---|---|
| A, сырой CUR: ~200 ресурсов × 24 ч × 30 д × 3 типа платы | 4.3×10⁵ | ~650 мс |
| B, свёртка день+сервис: ~25 сервисов × 30 д | 750 | ~1 мс |
| C, журнал снаружи | 0 | ~0 |

При A ломается не поиск: после загрузки `Dictionary` по id даёт O(1).
Ломается загрузка: каждый apply материализует и трекает все 4.3×10⁵
детей. Оптимистичная блокировка через `xmin` корня: любой `SaveChanges`
меняет версию строки Budget, параллельные apply того же бюджета
конфликтуют и ретраятся; при пачке CUR это hotspot, а не очередь
на словарь. Поздняя корректировка закрытого периода стоит столько же,
сколько обычный apply — снова полная загрузка, потому что коллекция
не выгружается вместе со статусом Closed.

При 50–100 клиентах N на агрегат не растёт: у каждого клиента свой
`Budget`. Растёт число агрегатов, и это даёт параллелизм, а не
конкуренцию за одну строку. Партиционирование Kafka по `account_id`
это использует: сообщения разных клиентов не сериализуются на одном
`xmin`.

## Последствия

Проще: `Budget` по-прежнему замыкает инварианты 1–7; тесты порогов,
идемпотентности и дельты не поднимают инфраструктуру. Write-hotspot
ограничен числом зёрен, не линий CUR.

Сложнее: ingestion обязан сворачивать вход до согласованного ключа.
«Запись» в Ubiquitous Language — это зерно, не строка провайдера.
Смена ключа зерна — ломающее изменение границы агрегата.

Цена: детализация «какая линия толкнула 80%» живёт во витрине
ingestion, не в Budgeting. Коррекция линии, не менявшая сумму зерна,
для бюджета невидима.

## Что заставит пересмотреть

- Зерно мельче дня+сервиса (час, ресурс, тип платы) → N снова
  растёт как в A; переход на C.
- Период длиннее месяца (квартал, год) при том же зерне:
  25 × 90 = 2.3×10³, 25 × 365 ≈ 9×10³ — выше потолка 10³
  записей на период → C.
- Один агрегат на несколько клиентов → N и `xmin` снова общие;
  партиции Kafka по `account_id` перестают снимать конкуренцию → C
  либо нарезка корня по клиенту.
- Требование трассировки до отдельной CUR-строки → зерно B
  недостаточно, коллекция в агрегате не подходит → C, журнал
  линий снаружи.
- Spent считается джобой из витрины раз в N минут
  → и B, и C вырождаются в `Budget.Reconcile(spent)`, журнала
  в Budgeting нет.
- Нет общего UoW журнала и агрегата (разные БД без outbox)
  → актуально только после перехода на C; нужен идемпотентный лог
  с другим протоколом, не уникальный ключ в той же транзакции.
