# CloudLens — план разработки

Рабочий документ. В новом чате: «читай `docs/plan.md`, мы на дне N, шаге M».

---

## Роли

| Кто | Что делает |
|---|---|
| **Cursor** | Пишет код. Все промпты на реализацию идут ему. |
| **Claude (чат с подключённой папкой / Claude Code)** | Составляет промпты для Cursor и ревьюит результат. Код сам не пишет. |
| **Вы** | Принимаете решения, запускаете `dotnet test`, коммитите. |

У Claude в оболочке нет `dotnet` — результат тестов показываете ему сами.

### Как начинать новый чат с Claude

```
Продолжаем CloudLens. Прочитай AGENTS.md, docs/plan.md,
docs/domain/invariants.md и docs/adr/. Мы на дне N, шаге M.
Твоя роль — промпты для Cursor и ревью. Код сам не пиши.
Дай промпт для шага M.
```

### После того как Cursor закончил шаг

```
Cursor сделал шаг M, dotnet test: <зелёный / вставить вывод>.
Посмотри результат в папке. Отчёт: что не так, что критично,
что отложить. Не переписывай.
```

### Если промпт от Claude слишком длинный

```
Короче. Цель и ограничения, детали реализации Cursor выберет сам.
```

## Ежедневные правила

- **Новый чат на каждый крупный шаг.** В Cursor — новая вкладка, в Claude Code — `/clear`. Длинная сессия деградирует.
- **Обсуждение — в Ask (Cursor) / plan mode (Claude Code, Shift+Tab дважды). Код — в Agent.** Архитектуру не обсуждают в режиме, который правит файлы.
- **Контекст подтягивать руками:** `@AGENTS.md`, `@папка`, `@файл`.
- **Коммит после каждого зелёного шага.** Осмысленное сообщение (`feat(budgeting): ...`, `test: ...`, `docs: ...`), никаких `...`. Тесты коммитить раньше реализации.
- **Правило вместо повтора.** Модель ошиблась дважды — допишите строку в `.cursor/rules/*.mdc` или `AGENTS.md`, отдельный коммит `rules: ...`.
- **Тест не компилируется ≠ тест упал.** Сменился API → правка теста допустима. Тест красный → чинить код, не тест.
- **Не полировать бесконечно.** Критерий «день закрыт» выполнен — идём дальше.

### Четыре вопроса, чтобы спорить с моделью без знания домена

1. Что из этого не понадобится в первой версии?
2. Какой инвариант перестанет проверяться доменным тестом, если сделать так?
3. Под какой масштаб ты это оптимизировал и откуда цифра?
4. Объясни решение, как будто я защищаю его на собеседовании, в трёх предложениях.

Частая ошибка моделей: оптимизируют под масштаб, которого нет, ценой того, что нужно сейчас.

## Словарь

- **CUR** — Cost and Usage Report, построчная детализация расходов от облака. Приходит повторно, уточняется, опаздывает — отсюда инварианты 1–3.
- **Зерно** — уровень детализации. У нас `(аккаунт, дата потребления, сервис)`, не сырая строка CUR. См. ADR-0001.
- **ADR** — Architecture Decision Record: контекст, варианты, решение, последствия, «что заставит пересмотреть».
- **Защёлка (latch)** — порог `Clear → Latched` даёт одно событие; повторно только после сброса.
- **Гистерезис** — сброс порога только при падении на 5 п.п. ниже (80% → сброс на 75%).

Руками: запустить, открыть CSV глазами.

### 2.2 — ADR-0002 (Cursor, Ask → Agent)
Шесть «правил в голове» из `invariants.md`. Главные три:

- закрытый период принимает начисления, но не даёт менять лимит (лимит — обещание, расход — факт; поздние корректировки CUR; пороги на закрытом периоде продолжают алертить);
- отрицательная сумма зерна и отрицательный `Spent` допустимы, пороги при этом `Clear` (запрет развёл бы журнал зёрен и `Spent`);
- 100% перезаряжается на 95% — намеренно.

Остальные одной строкой: «бюджет — один период» (+ глоссарий), `ChargeApplied` отложен до дня 4, порядок проверок в `ChangeLimit`.

Заодно убрать из «Что заставит пересмотреть» ADR-0001 строку про повторяющиеся бюджеты — перенести в ADR-0002.

### 2.3 — свёртка (Cursor)
CSV-строки → зерно `(account_id, usage_date, service)`.

- дедупликация «последняя побеждает» по `line_item_id` до суммирования (свёртка дедуплицирует внутри пачки, домен — между пачками; записать в глоссарий);
- округление один раз, на уровне зерна, до центов;
- нормализация сервиса та же, что в `ChargeKey`.

Тесты: 1000 строк → одна свёртка; разные дни / сервисы не схлопываются; регистр нормализуется.

### 2.4 — Application (Cursor)
Команды: `CreateBudget`, `ApplyCharges`, `ChangeLimit`, `ClosePeriod`. Запросы: `GetBudgetStatus`, `GetCostBreakdown`. Без MediatR, `ICommandHandler<TCommand, TResult>`, handler только оркеструет. Интерфейсы в `Abstractions/`.

### 2.5 — Infrastructure (Cursor)
EF Core 10 + PostgreSQL: конфигурация по файлу на агрегат, `Money`/`PeriodRange` owned types, backing fields, `UseXminAsConcurrencyToken` на `Budget`, витрина `daily_cost`, миграция `InitialCreate`. Ждать первых предупреждений от `TreatWarningsAsErrors`.

### 2.6 — интеграционные тесты (Cursor)
Testcontainers + PostgreSQL:
- круговой: сохранили → загрузили, защёлки, зёрна, `Spent` целы;
- параллельно одна свёртка двумя потоками → `Spent` растёт один раз;
- CSV → свёртка → применение → `Spent` = сумма округлённых зёрен.

Руками: убрать `xmin`, увидеть красный тест, вернуть.

### 2.7 — ревью (Claude)
Круговой тест восстанавливает всё? Свёртка не обходит инварианты (нормализация, валюта, дата)? Совпадает ли код с `invariants.md`?

## Как рассказывать проект на собеседовании

Через путь одной записи, а не списком технологий:

15 марта провайдер присылает CUR за 14-е. Ingestion читает из Kafka, отсеивает уже виденную пачку, сворачивает строки до зерна. Budgeting применяет: дата в периоде (инв. 8), зерно новое (инв. 1), стало 80.5% — порог `Clear → Latched`, событие. Событие пишется в outbox той же транзакцией, уходит в Kafka, приходит письмо.

16-го уточнение: та же строка дороже. Считается разница (инв. 2), 80.6%, порог уже `Latched` — письма нет (инв. 3).

17-го детектор по gRPC: 14-е — аномалия, 4.2σ. Заводится случай, LLM пишет объяснение. 18-го та же аномалия — новый случай не создаётся.

1 апреля период закрыт, лимит заморожен. 3 апреля поздняя строка за 29 марта — расход принят, лимит не меняется.
